# Fala 0.14.3 — conversation recovery and measured capacity

Date: 26 September 2026. The owner explicitly authorized paid OpenAI conversations and web transcription, Groq conversation backup, removal of daily app allowances, and publication to the website, internal testing and closed testing. The requested capacity target is 50 simultaneous learners.

## Changes and verification

Removed same-provider quota sleeps and client quota countdowns. A failed primary starts backup immediately; a slow primary starts backup after 1,200 ms. Both routes and their single repair share an 8,000 ms deadline. Only a validated result is saved, and the losing request is cancelled. Failed requests retain the draft and retry identity. Daily app/user allowances are disabled; the per-account 120-request/minute flood guard remains.

An operator-only diagnostic uses fixed synthetic content and reports numeric timing/token/capacity observations without saved learner context. The first live check also exposed an inappropriate offer to choose a cord after the learner said they had none. The final source preserves that stated fact in instructions and rejects such offers before playback. Subsequent live samples asked about class practice or the teacher instead.

The successful isolated Groq probe proves access, not backup capacity for a primary outage. Removing visible countdowns did not remove provider limits.

## Remaining capacity and latency work

Observed OpenAI headers report **500 requests/minute and 500,000 tokens/minute**; the corrected fixed context used 2,828 input tokens and roughly 120 output tokens. Groq reports **8,000 tokens/minute and 1,000 requests/day**. Its request-limit header means requests per day, not requests per minute.

At 50 learners sending once every ten seconds, the base demand is 300 requests/minute. Even this short fixed context would exceed 500,000 tokens/minute under sustained use; real later turns, repairs, starts, summaries and hedges require further headroom. Request an initial allowance around **500–1,000 conversation requests/minute and 2 million tokens/minute for each route intended to carry the entire load**, then size from measured real-session usage. This is a planning envelope with an explicit usage assumption, not a purchased reservation or an SLA.

The existing connection can invoke configured models but does not provide the account-admin access needed to buy higher provider capacity. The owner must use the existing organizations in [OpenAI Limits](https://platform.openai.com/settings/organization/limits) and [Groq Limits](https://console.groq.com/settings/limits) / [Billing](https://console.groq.com/settings/billing). Verify approved limits, funding and model access afterward using the fixed probes. Do not create accounts to bypass limits or expose keys. See the official [OpenAI limit guidance](https://developers.openai.com/api/docs/guides/rate-limits) and [Groq limits](https://console.groq.com/docs/rate-limits).

The **under-three-second target for 50 simultaneous requests was not achieved**. Higher throughput allowances do not by themselves guarantee lower latency. Further hosting/transport measurements are needed before buying a hosting plan or changing regions; the API and database are already colocated. Paid processing and account limits remain finite. No zero-outage claim is made.

The optional full-session production script was not run: it requires a dedicated test-only learner credential, because ordinary session endpoints use account history and retain aggregate rewards after conversation deletion. Physical Android recognition/playback and the changed web transcription route were not exercised with real audio in this release.
