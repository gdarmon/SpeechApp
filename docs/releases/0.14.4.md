# Fala 0.14.4 — release candidate, 27 September 2026

Publication and the final live measurements are pending. Do not infer a Play upload from a successful Vercel deployment.

## Changes

- Release SQL connections during AI generation using durable per-account claims, short transactions and stale-result fencing. Preserve account isolation, idempotency and reward ownership.
- Return the saved turn ID in `X-Fala-Turn-Id`; web renders the existing reply immediately instead of reloading the session. Older APIs retain the GET compatibility path.
- Permit spaced question reuse after two intervening exchanges while retaining immediate-loop, translation and answer-match validation. Keep final-turn continuation instructions consistent with closing the lesson.
- Prepare the full website/API on `https://fala-api.vercel.app`. Android's approved origin migration preserves encrypted device login and active-session preferences against the unchanged account database.
- A new Web Push key is needed because the previous private key is unavailable through the authorized connection. New subscriptions record their public key; the scheduler never sends/claims using another key. Account reminder times and opt-outs remain unchanged. The new browser origin requires notification permission again.
- A dedicated GitHub Actions schedule invokes the protected Vercel reminder endpoint every 15 minutes. Scheduling is best effort. Netlify must remain only as transitional URL compatibility for old clients until retired; do not enable two schedulers.

## Verification so far

213 backend tests passed after the reminder changes; one explicit concurrency test was skipped in the default suite and passed separately against PostgreSQL. Android unit tests, debug build, lint and instrumentation compilation passed with Java 21. The three browser suites passed the direct-reply path and legacy lost-response retry. Physical phone audio and a real Google sign-in were not performed by the agent.

The generation-claim migration was applied and RLS/private-role restrictions verified before dependent code deployment. No learner tables were copied for load tests.

## Measured results and scope

[Controlled local concurrency](../session-concurrency-2026-09-27.md): 50/50 full sessions completed; transaction acquisition p95 fell from 1,357.1 to 195.0 ms with a fixed 25 ms fake provider. This excludes hosting, real AI and audio.

The real full-session harness uses private `fala_latency_probe` tables, separately generated device tokens, Hebrew support, alternating Portuguese levels 1/3, assisted typed answers, ten turns, replay/isolation checks and a five-item review bound. Bursts are 35 seconds apart; this is not a sustained rapid-turn capacity guarantee. Reports contain no text, credentials or learner IDs.

These include failed requests and cold starts. Incomplete actors stop; later phases therefore contain fewer than 50 requests. The first run exposed 20 repetition-validation failures and two closing-turn validation failures. The second improved completion but still failed the reliability/speed gate. The third run still failed the reliability/speed gate: both primary attempts copied the previous answer pair; Groq then failed Hebrew validation and returned 429. Its one-call requests had p50 2.399 s/p95 3.044 s (544); requests with repair/fallback had p50 4.029 s/p95 5.337 s (52). The next candidate makes prior ideas and the exact required replacement explicit. SQL spans also showed occasional spikes, so the driver idle timeout was raised from 20 to 60 seconds to retain connections across typical reply pauses; the third run had SQL p95 268.7 ms versus 795.1 ms in the second. This is observational, not an isolated causal comparison.

A single synthetic audio round trip on the real website API succeeded: speech generation 2.449 s, transcription 1.260 s, Send-to-reply 3.607 s. This uses clean generated Portuguese audio, not a physical microphone or Android recognition/playback.

Optional reports: `hosted-sessions-50-1790504729528.json`, `hosted-sessions-50-1790505481611.json`, `hosted-audio-1790504386580.json` under ignored `artifacts/`. Maintained tables above are the durable record.

Google's sign-in script, stylesheet and button frame loaded with HTTP 200 on the new origin, with no browser page errors, after the owner added the authorized origin. This did not perform a real Google account login. An isolated Netlify draft forwarded health to Vercel, rejected unauthenticated dashboard reads, redirected web pages, accepted the exact legacy Origin through input validation, and rejected a foreign Origin with 403.

The fourth run failed on language mixing: both OpenAI attempts included Hebrew in Portuguese fields; the Groq attempt failed support-language validation and then received 429. The next candidate constrains language character classes and question counts in the provider's strict JSON Schema, retains the application validators, and explicitly lists recent questions to avoid. OpenAI documents support for string `pattern` constraints in [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs). This does not guarantee semantically correct teaching or sufficient backup capacity.

The legacy service-worker migration test passed in Chromium. It unregisters the old worker, clears only Fala shell caches, preserves an open page and follows the new origin on the next visit. `npm run dev` was changed to a loopback-only development server so local development cannot use production's proxy rules; local health and static-page smoke checks passed without cloud access.
